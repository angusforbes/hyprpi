# omnistation/: remote worlds, headless hyprpi on another machine

Any world (A to I) can be bound to a remote Linux machine: its agents run there and the laptop shows them. On the remote machine a headless hyprpi daemon and each agent run in their own tmux session under `~/.hyprpi-<letter>` (no Hyprland, panels or windows), so they keep running when ssh drops or the laptop sleeps. Two worlds can share one machine.

On the laptop an agent is a window on its world's workspaces, drawn locally (J471): pi's own editor, message and tool components run on the laptop, so typing and editing never cross the link. A finished message goes to the remote pi, which runs in RPC mode behind a small broker, and its events (streamed text, tool calls and results) come back and render locally. The window loads the session's history when it connects, and reconnects by itself after a dropped ssh, a hung one (nothing heard for 45 s, also before the broker answers), a new login, the laptop waking from sleep or the agent being started again. Its editor always takes typing: what you send while it's disconnected waits in an outbox (shown above the editor and in the footer) and goes out once, in order, after the reconnect; a message whose answer the link lost goes back into the editor, never sent twice. The footer's 📡 entry shows the link's true state: nothing while connected, "no answer for N s", "reconnecting… (N s; last: why)", "disconnected: why · retrying in N s", "login expired: run tsh login", or "stopped · waiting"; Enter on an empty editor retries at once (J543). Tests: `node test/remote-client-reconnect.mjs` (the window under a pty against a fake ssh and broker) and `node test/hbroker-socket.mjs`.

- `world`: the laptop side: `world X setup|new NAME|open NAME|status|stop NAME|binding` (X = the world letter). `world-h` is the J469 alias for `world H`.
- `remote-client.mjs`: the window `world X open NAME` starts (kitty, silently, on the world's first workspace). Keys: Enter sends (a steer while the agent works), Alt+Enter queues a follow-up, Esc interrupts, /model or Ctrl+L picks the model (type to filter), Ctrl+O expands tool output, Ctrl+D (on an empty editor) or /quit closes the window (the agent keeps running).
- `remote.sh`: runs ON the remote machine (copied by `world X setup`): install, start NAME, connect NAME, status, stop; attach NAME for the mirror fallback. It refuses to start while a secret (hyprpi-secrets, pi's auth.json and models.json, the search tool's token) is readable by others.
- `hbroker.mjs`: on the remote machine, keeps one agent's `pi --mode rpc` running with the hyprpi extension, serves it on `~/.hyprpi-<letter>/run/NAME.rpc.sock` for several clients at once, and answers pings so dead connections end. It never takes over or removes a live agent's socket (J543): `serve NAME -- -p …` (a one-shot pi) runs plain pi, a second broker for an agent refuses (exit 6; one per name by the lock `run/NAME.broker.lock`, held for the broker's life, taken over once when stale), it removes the socket file only while it's its own, and serves it again if something else removed it.
- `world-status.mjs`: one per remote world on the laptop (started by `world X open`, ends 10 min after the world's last window closes). It writes the same host-only files a sandboxed world's helper writes (`~/.local/state/hyprpi/worlds/world-<x>/windows.json` and `agents.json`, marked "badge": "📡"), from the window list and the remote daemon's own list (through `remote-control/rworld.mjs`, the phone server's bridge, so there is one source). So the world's agents appear in the finder (SUPER+SHIFT+SPACE, with ⏎ opening a window for an agent that has none), in summon (SUPER+S) and in the world's agents panel, marked 📡 where a sandbox's are 🐳. It never sends anything to an agent.
- `world X panel KIND` opens one of the world's panels (agents, room = Stream, search = Thoughts, board = Projects) in a laptop window; the panel itself runs on the remote machine (`remote.sh panel KIND`) through `panel-loop.sh`, which comes back by itself after a drop.
- Panels act on the laptop (J543): what a panel does "on the desktop" happens on the laptop, as in a local world. `panel-loop.sh` runs the panel's ssh through `pty-relay.py`, a small pty relay. In remote mode (HYPRPI_REMOTE_PANEL=1) the panels don't act on the remote machine; `lib/tui/laptop.mjs` writes a private request to the terminal instead (`ESC ] 5379 ; hyprpi ; base64 JSON BEL`). The relay takes it out of the output and runs `laptop-act.mjs`. The actions: Ctrl+click, click or ⏎ on an agent jumps to its laptop window, opening it first if it has none (also `world X focus NAME`). An http(s) link opens in the laptop's browser. A file link (a path on the remote machine) is copied to ~/Downloads/hyprpi-<x>/ and opened; a type that could run something gets only its folder opened. A job link or project row brings up the laptop's board panel, and /agents /room /search /board bring up the matching panel. Ctrl+N or /new runs `world X new`, then jumps to the new agent. Ctrl+V or SUPER+V in Thoughts with an image on the laptop's clipboard uploads it to ~/.hyprpi-<x>/clipboard/ (600) and types its remote path into the box, so ⏎ sends it to Thoughts-X as an image; text is pasted as text. Copying in the agents panel goes to the laptop's clipboard (OSC 52).
- The relay's checks: a request needs this run's nonce, which is never on a command line (J553: other users of the machine see those in ps). The remote command only says HYPRPI_LAPTOP_RELAY=ask; remote.sh turns its terminal's echo off and asks the relay with a private sequence, the relay types the nonce in (once a run, and never once the panel has started drawing), and remote.sh puts it in the panel's environment, which only its own user can read. It must follow a matching local input that the relay passed through itself, within 2.5 s, and each input is used once: a press or ⏎ for focus, open, file or panel; Ctrl+N or ⏎ for new; Ctrl+V or Shift+Insert for paste, so the clipboard is never read otherwise. A request must also be well formed and within 8 per 10 s. Anything else is dropped and never shown. Every panel, local or remote, cuts terminal commands out of what the daemon sends (an agent's OSC 52, title, hyperlink, DCS, a cursor or mode CSI, other controls; colours stay: `connect({ scrub: true })` in lib/client.mjs, J553), so a request an agent prints doesn't even reach the relay. Tests: `python3 test/pty-relay-unit.py`, `node test/laptop-tui-remote.mjs`, `node test/remote-panel-laptop.mjs` (the four real panels end to end, with a fake remote machine and stubs).
- Links in an agent's window (J553): what a remote agent prints names things on the remote machine, so its window's kitty (`world X open` sets its open_url_with) hands every Ctrl+clicked link to `laptop-act.mjs X url`: an http(s) link opens in the laptop's browser; a file:// link (file:///home/you/work/x.png, no host or localhost) is copied from the machine to ~/Downloads/hyprpi-<x>/ (600, at most 50 MB) and opened, and a type that could run something only gets its folder opened, as from the panels; any other link (another host, another scheme) is refused with a notification. Nothing a remote agent prints runs on the laptop. Windows opened before this change keep kitty's old opener until they're reopened. Test: `node test/remote-links.mjs`.
- The window looks like any agent window: hyprpi's kitty setup (your kitty.conf plus terminal-helpers/kitty/pi.conf), the laptop's pi theme and settings, pi's own footer (cwd, tokens, cost, context, model, and the remote agent's status line), and a title like G's ("📡 H: π - alpha - work").
- The fallback, J469's mirror (pi's terminal UI in remote tmux, every key over ssh): `world X start-mirror NAME` then `world X open-mirror NAME`.

The binding is private (never in this repo): `~/.config/hyprpi/remote/<letter>.json`, e.g. `{ "ssh": ["ssh", "me@my-server"], "label": "My server" }`. "ssh" is the argv that reaches the machine (plain ssh, or a Teleport `tsh ssh user@host`); "label" is optional; "workspace" overrides the world's first workspace, which otherwise comes from hyprpi's world layout (worldSize 10: H = 71). `world X binding` prints it as JSON for other tools (the phone app).

Learned on the first machine (J469): its git host was unreachable (setup copies the laptop's hyprpi instead), its outbound TLS is inspected by a local CA (remote.sh makes node trust the system bundle), and kitty's terminal type is unknown there (remote.sh falls back to xterm-256color for tmux). The model provider's key is set on the remote machine, privately. Which models it offers, pi's default and Thoughts' model come from [models.jsonc](models.jsonc) (J500: preset catalog / short / claude3gpt3 / laptop / custom, plus add, exclude, deny, default, thoughts), resolved on the laptop by lib/models-resolve.mjs and applied there by lib/nv-models.mjs during `world X setup`. A world picks its file with the binding's "models" (a path in this repo) and its key file with "modelsKeyFile" (world H: ~/.config/hyprpi-secrets/nvidia_inference_hub_key); without them it gets brev/models.jsonc and a Brev box's key path. `node lib/models-resolve.mjs --config omnistation/models.jsonc --show` prints the list.

One world per machine (J543): the remote daemon (its state is ~/.hyprpi-<letter>/state; lib/remote-world.mjs remoteHome) serves only its own world. Another world's Thoughts ("Thoughts-A") is refused with why (talk / ask / relayAsk), and so are its rooms, boards and Thoughts panel, and open_agent / spawn_agent / moves into it (a fake world A was made there before). Its "current" world is its own (not A).

New agents there (J543): open_agent, spawn_agent and a tinker job's "new" on the remote machine start the agent the remote.sh way (`remote.sh start SLUG` with the daemon's HYPRPI_START_* name, icon, folder, model, thinking, fork and workspace; id "<x>-<slug>"). The daemon's list marks it "opened", and the laptop's world-status.mjs opens its window once, silently, on its workspace (omnistation/auto-open.mjs). world-status also stays up while the world's panels are open.

Sounds (J543): the agents there have `bonk` / `ding` (remote.sh install writes them: they mark the agent blocked through hyprpi, with the message). The daemon keeps bonks, dings, "request" knocks and done chimes as notices in its list, and world-status plays each new one on the laptop: the bonk / ding toast is named "X 📡", and a click runs `hyprpi focus <x>-NAME`, which the laptop daemon hands to `world X focus NAME`.

Never an agent's identity in the daemon (J543): a daemon started by an agent's own `hyprpi ensure` used to carry HYPRPI_REMOTE_RPC / HYPRPI_NAME, so its one-shot pi calls became "hbroker serve <agent>" and stole that agent's socket (the window stuck on "reconnecting"). ensureDaemon and the daemon drop those variables, and pi-entry serves only an agent's own pi (HYPRPI_RPC_NAME, the slug), never a `pi -p`, `--mode` or `--no-session` call.

Panels on the laptop (J555, Angus: "13b sounds great lets do it!"): a remote world's panels can run HERE, the same panel code as a local world's, so typing, scrolling and clicks are local (keystroke-to-screen on the hub went from ~183 ms to ~8 ms, on H from ~190 ms to ~8 ms). `omnistation/world X panel KIND --link` opens one (the binding's "panels": "link" makes it the default; "pty", the old panel on the machine over ssh -t, stays as the fallback). Inside, omnistation/panel-link.sh runs `node mockups/KIND-tui.mjs X` with HYPRPI_REMOTE_LINK=X: lib/client.mjs then talks to the world's daemon through the world's link, omnistation/rlink.mjs: ONE ssh per world (`remote.sh link` → omnistation/rlink-remote.mjs there), a channel per panel connection, a ping every 15 s (45 s of silence = dead: the panels reconnect by themselves, the link comes back with backoff), an expired tsh login waits without starting ssh, and it ends 10 min after its last panel. `node omnistation/rlink.mjs X --status` says how it is. Over the same link (J555): Thoughts-H/I and their agents reach the laptop's Thoughts (Thoughts-A …: talk / ask_agent; the machine's daemon hands them to the attached link, rlink asks on the laptop and returns the answer; with no link they are refused with the reason, never a fake world), a process on the machine can ask the laptop to run an allow-listed op (`link.call` { op, args }: today "jot", lib/jot-relay-host.mjs), and every Projects panel's Decisions view (^F) lists all worlds' open decisions (H and I through their links, 📡; a world whose link is down is one "offline" line) and answers them in place. A pasted image is uploaded over the link (`link.upload`, ~/.hyprpi-<x>/clipboard, 600) before Thoughts gets it; clicks, links and job links run omnistation/laptop-act.mjs directly (lib/tui/laptop.mjs link mode).
Next: the room and talk between a remote world and the laptop's; the phone app (J472); bare paths (not file:// links) printed by a remote agent; restarting after the remote machine reboots; in the window, pi's other slash commands (/tree, /resume, /settings) and image paste.

Restarting a remote world's daemon (J530): `omnistation/world X restart-daemon`. It stops only this world's daemon (the pid in its lock file, checked to be exactly `node ~/hyprpi/bin/hyprpi daemon` with this world's state, and not signalled again if that pid changed), waits for an agent's own ensure to start a new one, else starts one in tmux, and reports success only when the new daemon answers. The agents' sessions are never touched. Never kill it by `pgrep -f "bin/hyprpi daemon"`: the tmux server's command line contains the same text, and killing that ends every agent's session.
