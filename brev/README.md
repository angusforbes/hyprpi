# brev/: a remote world on a Brev GPU instance

Status: tested end to end twice. J476 (2026-10-11) on a g4dn.xlarge (AWS, one T4 16 GB, 16 GB RAM, $0.63/h): hyprpi as world I, Qwen/Qwen2.5-3B-Instruct served by vLLM, and a pi agent (brev-alpha) answering and using its bash tool through it, in a window on the laptop. The T4 was too small for more than one model at a time, and an SD3.5 test ran its RAM out. J483 (2026-10-12) moved world I to an l40s-48gb.1x (Crusoe, one L40S 48 GB, 147 GB RAM, $1.74/h): Qwen2.5-3B and SDXL-Turbo resident side by side, and brev-alpha made a picture with `brev-image`.

Why Brev: its GPUs and its large disks, to run bigger models on the box itself, next to the agents. hyprpi runs on a GPU instance, and its agents use those local models (and, if you add one, a hosted provider).

Brev rents cloud VMs (Ubuntu, Docker, SSH, CUDA) billed per running hour. Its CLI writes your ~/.ssh config, so a plain `ssh <instance>` reaches the box. That is all hyprpi's remote-world code needs: everything in `omnistation/` works over any ssh argv. So a Brev box is just another remote world, with no Brev-specific code; this folder holds the setup steps, an example binding and `serve-model.sh`.

How it differs from the Omnistation world (H):

| Topic          | Omnistation     | Brev GPU box        |
| -------------- | --------------- | ------------------- |
| Login          | Teleport, hours | plain ssh           |
| GitHub, HF     | blocked         | work                |
| hyprpi install | copied tar      | copied tar for now  |
| Models         | hosted only     | local, hosted opt.  |
| GPU            | none            | on the box          |
| sudo, Docker   | no              | yes, NVIDIA runtime |
| Cost           | none per hour   | per hour, even idle |
| After a stop   | n/a             | depends on cloud    |
| Allowed work   | your org's      | personal / public   |

- hyprpi install: `world X setup` copies the laptop's committed master as a tar, as for H. A git clone works too (GitHub is reachable), but only once the public repo has the omnistation/ code.
- Crusoe (l40s-48gb.1x, J483): Ubuntu 22.04, Docker with the NVIDIA runtime, no Node, no /home/ubuntu/workspace; a 124 GB root disk plus a 118 GB /data disk, and both survived a stop/start (boot about 40 s). Its GPU driver (565, CUDA 12.7) is older than the newest vLLM image's CUDA, so serve with `VLLM_IMAGE=vllm/vllm-openai:v0.10.1.1` (cu128).
- After a stop: on AWS types (g4dn, g5, g6) the root EBS disk survives a stop, and there is no /home/ubuntu/workspace at first; ~/.cache, however, is a link to an instance-store NVMe (/opt/dlami/nvme), which is wiped. On types that come with /home/ubuntu/workspace, only that folder survives. Either way: keep everything under /home/ubuntu/workspace (create it on AWS), never in ~/.cache.
- Allowed work: check your organisation's rules for what may run on a cloud box; typically personal experiments and public work only, with no company code, keys or internal names there.

Pricing for NVIDIA employees (seen in Brev's console, 2026-10-12): compute up to $0.35/h and storage up to $0.10/h are free, and the console shows such a configuration as "Free" (e.g. Nebius cpu-d3.8vcpu-32gb with 256 GiB: $0.32/h + $0.04/h). The CLI (`brev search`, `brev create`) shows only list prices, so create a box that should be free from the console, where the price is shown. GPU types cost more than $0.35/h; whether the first $0.35/h of them is free isn't known yet (check Billing & Usage).

## Setup (as tested)

1. Pick a STOPPABLE GPU type: `brev search gpu --stoppable --sort price --wide` (Features column: S = stoppable; the others can only be deleted, so they bill until then). Ask Angus first, with the type, its $/h and the S flag. Tested: g4dn.xlarge (T4 16 GB, 16 GB RAM, $0.63/h: one small model at a time) and l40s-48gb.1x (Crusoe, L40S 48 GB, 147 GB RAM, $1.74/h: a text model and an image model side by side). Avoid 1-vCPU / 4 GB RAM types: too small for vLLM plus pi.
2. Create it with a disk that fits the models: `brev create hyprpi-gpu --type g4dn.xlarge --min-disk 100 --jupyter=false -d` (the default is 500 GB, billed per GB-month even while stopped). Wait until `brev ls` says READY (about 5 min), then `brev refresh` (the IP can change after each start) and check `ssh hyprpi-gpu nvidia-smi`.
3. Bind a free world letter to it, privately: copy `brev/binding.example.json` to `~/.config/hyprpi/remote/<letter>.json` (600) and set the host. Its "prefix" starts every agent's name there (e.g. brev-). Tested as world I (workspaces 81-90).
4. Keep what must survive a stop under workspace, first:
   - `mkdir -p -m 700 ~/workspace/.hyprpi-<x> ~/workspace/.pi ~/workspace/work`, then links `~/.hyprpi-<x>`, `~/.pi` and `~/work` to them (remote.sh accepts linked folders since J476);
   - `chmod go-w ~ ~/.config`: the image ships them group-writable, and remote.sh refuses to start until they aren't;
   - `HF_HOME=/home/ubuntu/workspace/.cache/huggingface` in ~/.bashrc (serve-model.sh mounts that path into the vLLM container).
5. On the box, once: Node 22+ (the image has none; tmux, git and Docker are there). For example the nodejs.org tarball under workspace, linked into ~/.local/bin, which remote.sh puts on PATH:
   - `ssh hyprpi-gpu 'cd ~/workspace && curl -fsSL https://nodejs.org/dist/v22.20.0/node-v22.20.0-linux-x64.tar.xz | tar -xJ && ln -sfn ~/workspace/node-v22.20.0-linux-x64 ~/workspace/node && mkdir -p ~/.local/bin && for b in node npm npx; do ln -sf ~/workspace/node/bin/$b ~/.local/bin/$b; done'`
6. `omnistation/world X setup`: copies remote.sh and hbroker.mjs into `~/.hyprpi-<x>`, copies hyprpi to ~/hyprpi, installs Pi (the laptop's version) into ~/.local, and writes the headless config. For a Brev box it first turns on the laptop's idle auto-stop for it (step 10c) and says so.
7. Serve a model: `scp brev/serve-model.sh hyprpi-gpu:workspace/`, then `ssh hyprpi-gpu workspace/serve-model.sh Qwen/Qwen2.5-3B-Instruct`. It runs `vllm/vllm-openai` in Docker on 127.0.0.1:8000 (half precision on a T4, which has no bfloat16; tool calls on, hermes parser), waits until it answers, and adds the model to pi's `~/.pi/agent/models.json` as provider local-vllm. First pull of the image: about 7 min; first start of a 3B model: about 3 min (download, compile, CUDA graphs). Gated models (e.g. Llama) need a Hugging Face token: make a separate read-only one for Brev and put it on the box yourself, `ssh hyprpi-gpu 'mkdir -p -m700 ~/workspace/.secrets && cat > ~/workspace/.secrets/hf_token && chmod 600 ~/workspace/.secrets/hf_token'` (paste, Ctrl-D); serve-model.sh passes it to vLLM as HF_TOKEN (accept each model's licence on its page first). Hosted models (J499): put the box's own dedicated NVIDIA Inference Hub key (sk-…; an nvapi- build.nvidia.com key gets 401) in `~/workspace/.secrets/nv_inference_key` yourself (600 in a 700 folder; the command is just below this step, paste then Ctrl-D). `world X setup` then runs lib/nv-models.mjs on the box: provider nv-inference in pi's models.json with the models chosen in [brev/models.jsonc](models.jsonc): preset "short" (Opus 5.5, Sonnet 5.5, Haiku 4.5, GPT-6.1 sol, Gemini 3.1 Pro), "laptop" (every nv-inference model on this laptop's scoped list, minus a deny list such as Kimi) or "custom", plus add / exclude lines and the default; lib/models-resolve.mjs resolves it on the laptop (the same resolver as omnistation/models.jsonc and docker/world/models.jsonc; preset "catalog" = hyprpi's standard tested list) (`node brev/models-resolve.mjs --show` prints the list), the key read at request time by a !command, and the default model (Opus 5.5) as pi's default for new agents and as Thoughts' model. The local vLLM model stays listed. Without a key it says so and changes nothing. To offer another model, edit models.jsonc and run `world X setup` again; agents already running see it after a restart.
   - `ssh hyprpi-gpu 'mkdir -p -m700 ~/workspace/.secrets && cat > ~/workspace/.secrets/nv_inference_key && chmod 600 ~/workspace/.secrets/nv_inference_key'`
8. Images (optional): `ssh hyprpi-gpu mkdir -p workspace/brev-image .local/bin`, `scp brev/image/server.py brev/image/serve-image.sh hyprpi-gpu:workspace/brev-image/` and `scp brev/image/brev-image hyprpi-gpu:.local/bin/`, then `ssh hyprpi-gpu workspace/brev-image/serve-image.sh`. It keeps SDXL-Turbo resident on the GPU (about 7.5 GB) as a small service on 127.0.0.1:8001; start vLLM with `GPU_UTIL=0.6` so both fit on a 48 GB GPU (serve-model.sh keeps GPU_UTIL and VLLM_IMAGE in ~/workspace/.serve.env, so later restarts use them too). An agent runs `brev-image "<prompt>"` with its bash tool and gets the PNG's path (about 0.3–0.9 s at 512², 4 steps, on an L40S). `omnistation/world X images` copies new images to ~/Brev on the laptop and prints them as file:// links.
9. Agents: `omnistation/world X new NAME` (or SUPER+A on the world's workspaces) starts brev-NAME and opens its window on the laptop; `/model` there picks the model. No hosted key is on the box unless you add a separate, scoped one.
10. Panels (J480): on the world's workspaces (81–90 for I) the panel keys bring the world's own Stream, Projects, Thoughts and agents panels, which run on the box against its daemon, each in a laptop window that comes back by itself after a drop (`omnistation/world X panel room|board|search|agents` opens one). Thoughts-X uses the binding's "thoughtsModel" (e.g. `local-vllm/Qwen/Qwen2.5-3B-Instruct`), passed on by `world X setup`. Brev's ssh config already shares one connection per box (ControlMaster), so every window is one session on it: raise sshd's limit of 10 once, `ssh hyprpi-gpu 'echo MaxSessions 64 | sudo tee /etc/ssh/sshd_config.d/90-hyprpi.conf && sudo systemctl reload ssh'`.
10b. Shared folder (J494): `~/Brev` on the laptop and `~/workspace/shared` on the box sync both ways with Unison 2.54.0 (the upstream static binary, the same on both sides: `~/.local/lib/unison-2.54.0/unison` on the laptop, `~/.local/bin/unison` on the box). `brev/sync/brev-sync` runs every 2 min from the systemd user timer `brev-sync.timer` (install: `systemctl --user link ~/Harness/hyprpi/brev/sync/brev-sync.{service,timer}` then `systemctl --user enable --now brev-sync.timer`). Each run first asks `brev ls` whether the box is RUNNING and otherwise exits quietly, so a stopped box is never started or woken, and the log gets one "paused" line rather than one per run. It then pulls brev-image's new PNGs from `~/workspace/outputs` into `~/Brev` and syncs. Conflicts: the newer copy wins and the other is kept as "name (conflict_on_DATE).ext"; overwritten or deleted files are also kept in `~/.unison/backup` on the side that lost them. The box folder is deliberately not `~/workspace/outputs`, so files from the laptop never count as box activity for an idle check that watches outputs and the hyprpi sessions; ssh itself doesn't count either. `brev-sync status` shows the state, the failures in a row and the log (`~/.local/state/brev-sync/`). Failures (J497): a run that fails while the box is RUNNING (ssh, Unison, or the image pull) exits 1, so `systemctl --user status brev-sync` shows it failed; a stopped box, or `brev ls` failing, is a quiet pause and exits 0. After 3 failures in a row (`BREV_SYNC_ALERT_AFTER`) Angus gets ONE alert: a ⚠ line in world A's Thoughts thread (`hyprpi thoughts alert A …`; `BREV_SYNC_ALERT_WORLD`) and a desktop notification, and one "working again" when a run next succeeds; nothing repeats every 2 min. One alert per outage: a stopped-box pause in the middle doesn't start a new one (J497 v2); a box that leaves RUNNING during a failed run is a pause (exit 0), not a failure; an alert that reached no channel isn't counted as sent and is tried again on the next failed run. Test: `bash test/brev-sync-failures.sh`. The phone app's Files tab shows `~/Brev` too.
10c. Auto-stop (J498, every instance since J516): `brev/autostop/brev-autostop` stops any Brev box after its idle minutes (default 45), so none bills for nothing. It runs every 5 min from the laptop's systemd user timer `brev-autostop.timer`. Step 6 (`world X setup`) turns it on for a new box by itself (`brev-autostop setup-hook`): it links the script into ~/.local/bin, enables the timer if it isn't yet, registers the instance in the config and prints "auto-stop is on for NAME: stopped after 45 idle minutes …"; re-runs change nothing. For a box set up some other way (a plain training box): `brev-autostop install NAME`.
   - Which boxes: every instance `brev ls` shows RUNNING, each on its own, including ones it has never seen (they get the default). STOPPED or missing boxes, or `brev ls` failing, are left alone (one log line per change, no repeats). Config: `~/.config/hyprpi/brev-autostop.conf` (made from `brev/autostop/brev-autostop.conf.example` on first use; `brev-autostop config` prints the path): `default_idle_min 45`, `gpu_busy_pct 10`, `idle NAME MIN` for one box's own limit, `exclude NAME` for a box it must never probe or stop (keep such names in your live config only, not in this repo), `box NAME` (registered by setup). Changes apply at the next run. With no config file at all it does nothing until `brev-autostop install` makes one.
   - Activity, read over one read-only ssh command per box (its own connection, J512):
     - the newest change to any hyprpi world's sessions, Thoughts threads and boards there (`~/.hyprpi-*/…`), brev-image's PNGs (`~/workspace/outputs`), and the shared folder `~/workspace/shared` (a recent change, or a listing that differs from the last run, since Unison keeps a copied file's original mtime);
     - vLLM: its `/metrics` count of finished requests moved since the last run, or a request is running now;
     - the GPU: `nvidia-smi` utilisation above `gpu_busy_pct` in any of 3 samples a second apart (any GPU). So a training run that keeps the GPU busy keeps its box up without a pause.
   An ssh login by itself changes none of these. A box that has just started gets its full idle time even if every file is old. A box that can't be read over ssh is never stopped on a guess. When a box has been idle long enough it runs `brev stop` (the workspace is kept) and sends ONE notice naming the box: a desktop notification and a ⚠ line in world A's Thoughts thread (`hyprpi thoughts alert A`). A failed stop alerts once (critical), then retries hourly without new alerts. One run at a time (a lock); a pause given while a run is probing still holds.
   - A box stuck UNHEALTHY (J523, Angus: "if it's unhealthy stop it and alert me"): Brev may still bill a box that went UNHEALTHY, or that sits in a failed stop. After `default_unhealthy_min` (45) minutes in such a state without a break (`unhealthy NAME MIN` for one box), it runs `brev stop` once and sends one alert with the status `brev ls` gives right after. If the stop fails or lands in a failed-stop state at once, that alert says so (critical); if a failed state comes later (STOPPING, then stopping_failed: J512), one more alert says so. After that it only retries at most hourly, quietly, and sends one "STOPPED now" notice when the box does stop. While the box is STOPPING after its stop it just follows it. A paused box is never stopped: it gets that alert only. Excluded boxes are never touched.
   - Pausing a training box (belt and braces, e.g. while it loads data with the GPU idle): `brev-autostop pause NAME 24h` (m / h / d), or `brev-autostop pause NAME` until `brev-autostop resume NAME`. Without a NAME it pauses every box. `brev-autostop status` lists every box with its state, limit, last activity and pause, then the log (`~/.local/state/brev-autostop/`). `BREV_AUTOSTOP_DRY=1` only says what it would do. Test: `bash test/brev-autostop.sh` (stubs for brev, ssh, curl, nvidia-smi, systemctl and the notices; the real probe runs against fixture files; it also runs `omnistation/world I setup` on a scratch binding).
   - No box-side backstop: Linkpath's test (J512, below) showed an in-box shutdown leaves Brev's control plane stuck, so the laptop timer is the only auto-stop.
11. Between sessions: stop the agents and the box: `omnistation/world X stop all`, `brev stop hyprpi-gpu`. An idle GPU still bills by the hour. Afterwards (ask first, it spends credits): `brev start hyprpi-gpu`, `brev refresh`, `ssh hyprpi-gpu workspace/serve-model.sh` (restarts the last model) and `workspace/brev-image/serve-image.sh`, then `omnistation/world X recover`, which waits for ssh and starts and opens every agent that has a session there. Tested (J476): boot about 1 min, workspace, sessions and the Docker image all intact, the model back in about 4 min, and the agent resumed its conversation. A laptop window still open from before the stop reconnects by itself (it waits while the agent is stopped), and recover doesn't open a second one (J479). Leave `recover --start-desktop` unused: it is for Omnistation.

## What the T4 test showed

- vLLM 0.31 runs on a T4 (compute capability 7.5) with the TRITON_ATTN backend (FlashAttention 2 needs 8.0+); a 3B model in fp16 plus a 32k context uses about 13 GB of the 15 GB.
- Qwen2.5-3B-Instruct answers in about 1-2 s and makes simple tool calls (it ran `nvidia-smi -L` through pi's bash tool), but it is weak as an agent. A 7B AWQ model (or a bigger GPU) is the next step.
- pi's system prompt alone is about 7k tokens, so keep the context at 32k or more.

## Tailscale (optional, J525)

A world's machine can join Angus's tailnet, for direct remote control (Tailscale SSH, its MagicDNS name, the phone's tailnet). It's off unless the binding (`~/.config/hyprpi/remote/<letter>.json`) has `"tailscale": true`, or `"tailscale": { "hostname": "…", "ssh": true, "authKeyFile": "…" }`. Then `omnistation/world X setup` runs brev/tailscale/ts-setup: it installs Tailscale on the machine if needed and joins as the hostname (default: the ssh host name), with Tailscale SSH unless `"ssh": false`. A machine already in the tailnet is left as it is.

The auth key: Angus makes it in the Tailscale admin console under Settings, Keys, Generate auth key: reusable off, ephemeral off, no tags (an untagged key: the machine joins as one of his own devices, on the same network as the others; his choice, 2026-10-12), and a short expiry, since it's only used to join. He puts it on the laptop himself, 600 in a 700 folder (default path `~/.config/hyprpi-secrets/tailscale-authkey`):

- `mkdir -p -m700 ~/.config/hyprpi-secrets && install -m600 /dev/stdin ~/.config/hyprpi-secrets/tailscale-authkey` (paste, Enter, Ctrl-D)

Setup sends it to the machine on stdin over ssh; there it goes into a 600 temp file for `tailscale up` and is removed at once, never on a command line, never printed. Untagged means the machine is his device: its node key expires like any device's (after it joins, open Machines in the admin console and disable key expiry for it, or it drops off the tailnet in a few months), and Tailscale SSH may ask him to confirm in a browser (check mode). If that gets in the way, plain ssh to its tailnet name or IP works without Tailscale SSH. (A tagged key would avoid both, but needs a tag owner and an SSH rule in the tailnet's access controls.) Test: `bash test/tailscale-setup.sh` (a fake ssh and tailscale; no real tailnet).

## Notes for long jobs (e.g. RL training, J512)

- Stop the box with `brev stop NAME` only. Never shut it down from inside (`sudo shutdown -h now`): tested 2026-10-12 on the Crusoe L40S, Brev listed it STOPPED after about 3 minutes, but its control plane kept it as "running", so `brev start` failed ("invalid environment status transition from running to starting"). After a `brev stop` it was stuck in "stopping_failed" and still couldn't be started. So an in-box idle shutdown is not a safe backstop.
- The laptop's auto-stop (step 10c, every 5 min) stops any box after its idle minutes (default 45). A training run that keeps the GPU above 10% counts as activity, so it keeps its box up by itself; still pause the box for the job, in case the GPU idles for a while (data loading, a stall): `brev-autostop pause NAME 24h` (or `pause NAME` until `brev-autostop resume NAME`). `brev-autostop status` shows what it saw last for each box.
- An idle hyprpi there doesn't keep the box busy. Its Thoughts may act once after a start (e.g. tidy a card), which counts as activity once, then it stays quiet.
- Keep checkpoints, datasets and logs under /home/ubuntu/workspace (a stop keeps it), and copy results to the laptop with the shared folder (brev/sync) or `omnistation/world X images`.
- Ask Angus before `brev create` or `brev start` (type, $/h, stoppable), and stop the box when the job ends.

## Rules for this world

1. Personal experiments and public work only.
2. Ask Angus before `brev create` or `brev start`; stop the box when you're done: it bills while running, idle or not.
3. Rebuild it per project or milestone; the setup above is cheap to repeat.
4. Watch the credit balance: running out can delete instances, and deleted data can't be recovered.
